# Energy Saving Recommendations

Цей файл містить робочий список рекомендацій для поступового зменшення
енергоспоживання контролера automatic-watering-hub.

## Виконано: Wi-Fi power save

- Wi-Fi стартує під час `setup()`, бо NTP-синхронізація потрібна для scheduled watering.
- Після старту Wi-Fi вмикається `WIFI_PS_MAX_MODEM`.
- HTTPS API та OTA стартують після спроби підключення Wi-Fi.

## Виконано: BLE advertising power save

- BLE використовує fast advertising перші 5 хвилин після старту.
- Після цього BLE перемикається на slow advertising і залишається доступним для
  підключення.
- Після disconnect advertising запускається повторно в поточному режимі.

Майбутня оптимізація:

- Додати фізичну кнопку або інший wake/config input.
- Після цього можна буде повністю вимикати BLE advertising і вмикати його тільки
  за дією користувача.

## Пріоритет 1: idle loop і sleep

Поточний стан:

- `loop()` у `src/main.cpp` виконується постійно.
- Навіть коли датчики ще не треба читати, CPU постійно перевіряє сервіси.
- Немає `delay`, light sleep або планування найближчої події.

Рекомендації:

- Додати планувальник найближчої події:
  - наступне читання лічильника води;
  - наступне читання датчика тиску;
  - наступне читання датчиків вологості;
  - час закриття відкритого клапана;
  - retry-delay для зони;
  - службові таймаути Wi-Fi/BLE/OTA.
- Якщо немає відкритого клапана, активного Wi-Fi API, OTA або BLE-з'єднання,
  переходити в `esp_light_sleep_start()`.
- Для короткого першого кроку додати хоча б невеликий `delay(...)` у кінці
  idle-циклу, але цільовий варіант - саме light sleep.
- Окремо перевірити, як PCNT поводиться в light sleep для поточного ESP32 і
  обраної версії ESP-IDF/Arduino core.

Очікуваний ефект:

- Значна економія CPU-частини, особливо коли Wi-Fi/BLE вже обмежені.

## Пріоритет 2: логування і метрики

Поточний стан:

- `Logger::begin()` завжди створює FreeRTOS task `log-delivery`.
- Кожне штатне читання сенсорів викликає `Logger::sendSensorReading(...)`.
- Для remote logging кожна подія може створювати окремий HTTPS POST.
- HTTPS-запити тримають Wi-Fi активним і коштують багато енергії.

Рекомендації:

- Не створювати `log-delivery` task, якщо `remoteLogUrl` порожній і BLE-логування
  не потрібне.
- Розділити режими логування:
  - normal: тільки помилки, попередження і важливі події;
  - debug: детальні сенсорні метрики;
  - maintenance: повне логування під час налаштування.
- Батчити сенсорні покази:
  - накопичувати кілька вимірів;
  - відправляти одним HTTPS-запитом;
  - відправляти тільки у Wi-Fi-вікні.
- Не надсилати однакові або незначно змінені значення, якщо зміна нижче
  налаштованого порогу.

Очікуваний ефект:

- Велика економія, якщо remote logging увімкнений.

## Пріоритет 3: живлення Modbus-датчиків і RS485

Поточний стан:

- SoilSensor і PressureSensor читаються за інтервалами.
- Код не керує живленням Modbus-датчиків.
- Код не керує живленням UART-to-RS485 модуля.
- Якщо датчики постійно живляться від 24 В, їх споживання може бути більшим за
  споживання ESP32 в idle.

Рекомендації:

- Додати load switch або MOSFET для живлення:
  - Modbus soil sensors;
  - pressure sensor;
  - UART-to-RS485 converter, якщо він не потрібен постійно.
- Перед читанням:
  - увімкнути живлення;
  - почекати стабілізацію датчика;
  - виконати Modbus-запит;
  - вимкнути живлення.
- Додати налаштування warm-up delay для різних типів датчиків.
- Залишити датчики вимкненими між читаннями в idle-режимі.

Очікуваний ефект:

- Потенційно найбільша системна економія, якщо зовнішні датчики зараз живляться
  постійно.

## Пріоритет 4: водяні лічильники

Поточний стан:

- WaterCounter використовує ESP32 PCNT.
- Лічильники читаються за інтервалом, але імпульси накопичуються апаратним
  лічильником.
- README вже вказує бажаний напрямок: прокидатися по перериванню.

Рекомендації:

- Перевірити, чи поточний PCNT може рахувати імпульси у вибраному sleep-режимі.
- Якщо PCNT не працює в потрібному sleep-режимі, розглянути wake-up від GPIO.
- Для idle-режиму не читати всі лічильники часто, якщо немає ознак протоку.
- Для аварійного виявлення протоку краще прокидатися від імпульсу, а не
  опитувати кожні кілька хвилин.

Очікуваний ефект:

- Дозволяє довше спати без втрати подій протоку.

## Пріоритет 5: клапани і реле

Поточний стан:

- `Valve::open()` тримає GPIO у `HIGH`, доки клапан відкритий.
- Звичайні 24 VAC клапани споживають струм весь час відкриття.
- Реле-модуль також може споживати струм котушкою весь час відкриття.

Рекомендації:

- Якщо система має працювати від батареї або сонця, розглянути:
  - latch-реле;
  - latch-соленоїди;
  - драйвер клапанів із коротким імпульсом відкриття/закриття.
- Якщо залишаються звичайні 24 VAC клапани, оптимізувати час поливу і не
  тримати клапани відкритими довше, ніж потрібно.

Очікуваний ефект:

- Важливо для автономного живлення. Під час поливу основне споживання може бути
  саме в клапанах і реле, а не в контролері.

## Рекомендований порядок робіт

1. Додати idle/light sleep між найближчими подіями.
2. Переробити логування на батчі й режими.
3. Додати кероване живлення Modbus-датчиків і RS485.
4. Дослідити wake-up від водяних лічильників.
5. Оцінити latch-рішення для клапанів, якщо потрібне автономне живлення.

## Відкриті питання

- Чи живляться Modbus-датчики постійно від 24 В?
- Чи можна апаратно вимикати живлення RS485 і датчиків?
- Яке цільове живлення: мережа 220 В, UPS, батарея, сонячна панель?
- Чи критично не пропускати жоден імпульс лічильника води під час sleep?
