# automatic-watering-hub

`automatic-watering-hub` - це контролер автоматичного поливу на ESP32 для
керування зонами поливу, збору показників із датчиків і віддаленого
налаштування через мобільний додаток.

Проект орієнтований на приватну або невелику локальну систему поливу, де
потрібно не просто вмикати клапани за таймером, а враховувати вологість грунту,
витрату води, тиск у системі, безпечне ручне керування і можливість діагностики.

## Що вміє система

- Автоматично запускати полив, коли вологість грунту нижче заданого порогу.
- Зупиняти або не запускати полив, коли вологість достатня.
- Керувати кількома зонами поливу через клапани.
- Працювати з Modbus-датчиками вологості грунту і датчиком тиску.
- Рахувати витрату води через імпульсні лічильники.
- Виявляти підозрілий потік води, коли система очікує, що клапани закриті.
- Давати користувачу ручне відкриття клапана на заданий час.
- Налаштовувати Wi-Fi через захищений BLE.
- Керувати системою через локальний HTTPS API.
- Відправляти логи і метрики на сервер для історії, графіків і push-сповіщень.
- Оновлювати firmware через Wi-Fi після першого USB-прошивання.

## Основна ідея

Контролер постійно підтримує модель системи: які датчики підключені, які зони
належать до яких датчиків вологості, які клапани відкриті, коли востаннє
поливалась зона і коли треба виконати наступну перевірку.

Коли датчик вологості показує, що грунт пересох, контролер ставить відповідні
зони в чергу на полив. Полив не виконується хаотично: зони відкриваються
послідовно, кожна на налаштовану тривалість. Після поливу зони система витримує
retry-delay, щоб вода встигла розподілитися і щоб не поливати ту саму зону
занадто часто.

Якщо вологість піднімається вище верхнього порогу, система більше не вважає
цю зону кандидатом на полив. Так контролер працює не тільки як таймер, а як
простий автомат прийняття рішень на основі стану грунту.

## Типовий сценарій роботи

1. Контролер стартує, читає налаштування з NVS і підключається до Wi-Fi.
2. Синхронізує час через інтернет, якщо Wi-Fi доступний.
3. Запускає BLE для локального налаштування з телефону.
4. Запускає HTTPS API для керування в локальній мережі.
5. Регулярно читає датчики вологості, тиску і лічильники води.
6. За потреби планує або виконує полив зон.
7. Логує події та сенсорні метрики локально, через BLE або на сервер.
8. Контролює, щоб ручне відкриття клапана не перевищувало дозволений час.

## Ключові фічі

### Автоматичний полив за вологістю

Користувач налаштовує два пороги вологості:

- нижній поріг, нижче якого треба запускати полив;
- верхній поріг, вище якого полив більше не потрібен.

Кожна зона поливу прив'язується до конкретного датчика вологості. Це дозволяє
одному контролеру керувати кількома ділянками з різними умовами.

### Послідовне керування зонами

Система відкриває клапани по одному. Для кожної зони задається:

- назва;
- GPIO pin клапана;
- датчик вологості, який відповідає за цю зону;
- тривалість поливу;
- пауза перед повторним поливом.

Такий підхід зменшує навантаження на водяну систему і дає передбачувану логіку
поливу.

### Сенсори і контроль стану

Проект підтримує кілька типів сенсорів:

- Modbus-датчики вологості грунту;
- Modbus-датчик тиску;
- імпульсні лічильники води.

Показники використовуються не тільки для UI, а й для діагностики: наприклад,
витрата води при закритих клапанах може означати протікання або відкриту
зовнішню точку водозабору.

### BLE-налаштування

BLE використовується як безпечний локальний канал першого налаштування.
Через BLE мобільний додаток може:

- прочитати поточні Wi-Fi settings;
- записати нові Wi-Fi settings;
- отримати IP-адресу контролера;
- отримати API access token для HTTPS API;
- отримувати log notifications під час діагностики.

Доступ до BLE characteristics захищений зашифрованим authenticated pairing із
passkey.

### Локальний HTTPS API

Після підключення до Wi-Fi контролер підіймає HTTPS API в локальній мережі.
Через нього мобільний додаток може:

- отримати поточні налаштування;
- зберегти нові налаштування;
- отримати останні метрики сенсорів;
- вручну відкрити клапан на заданий час;
- виконати службову Modbus-операцію, наприклад зміну slave address.

API захищений bearer token, який генерується контролером і доступний лише через
захищений BLE.

### Сервер, логи і графіки

Контролер може відправляти telemetry на сервер:

- logs - події, помилки, попередження і діагностичні повідомлення;
- metrics - показники сенсорів для історії і графіків.

Сервер зберігає ці дані, а мобільний додаток може використовувати їх для:

- push-сповіщень про важливі події;
- журналу логів;
- графіків вологості, температури, тиску і витрати води;
- короткої статистики за вибраний період.

## Налаштування

Більшість параметрів системи винесені в налаштування:

- Wi-Fi SSID і password;
- інтервали читання датчиків у idle і watering режимах;
- пороги вологості;
- режим старту поливу: одразу або в межах налаштованого вікна поливу;
- тривалість поливу однієї зони;
- пауза перед повторним поливом зони;
- максимальна тривалість ручного відкриття клапана;
- список клапанів;
- список датчиків вологості;
- датчик тиску;
- магістральний і додаткові лічильники води;
- server URL і token для remote logs/metrics.

Після збереження частини налаштувань контролер перезапускається, щоб підняти
сервіси з новою конфігурацією.

## Архітектура на високому рівні

Проект розділений на кілька логічних частин:

- `Hub` - збирає основні апаратні компоненти в одну модель системи.
- `AutomaticWatering` - приймає рішення про автоматичний полив.
- `Valve` - керує відкриттям і закриттям клапанів.
- `Sensor` - читає тиск, вологість і лічильники води.
- `Setting` - зберігає і валідує конфігурацію.
- `ApiBluetooth` - BLE-налаштування і локальна діагностика.
- `ApiWifi` - HTTPS API для мобільного додатку.
- `Connectivity` - Wi-Fi і OTA-оновлення.
- `Logging` - логи, BLE notifications і remote delivery.
- `Clock` - синхронізація часу.
- `Hypervisor` - службовий контроль стану системи.

Це не великий framework, а набір невеликих сервісів навколо головного циклу
ESP32.

## Безпека

У проекті є кілька рівнів захисту:

- Wi-Fi credentials доступні тільки через BLE.
- BLE вимагає зашифрованого authenticated pairing.
- HTTPS API вимагає bearer token.
- API token генерується випадково і зберігається в NVS.
- OTA-оновлення захищене тим самим token.
- Server ingest використовує окремий token для remote logs і metrics.

Важливе обмеження: ArduinoOTA не забезпечує повну криптографічну модель
оновлення firmware. Тому Wi-Fi мережа має бути довіреною, а access token не
можна передавати стороннім.

## Енергоощадність

Проект поступово рухається до меншого енергоспоживання:

- Wi-Fi використовує modem power save.
- BLE після стартового вікна переходить у slow advertising.
- Головний loop має idle delay, щоб CPU не працював у busy-loop.
- У планах - light sleep, кероване живлення Modbus-датчиків і wake-up від
  водяних лічильників.

Поточний пріоритет - зберегти доступність BLE для налаштування і не втратити
важливі події, наприклад імпульси лічильника води.
